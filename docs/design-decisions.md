## 1. 토큰 전략 — Stateless Access + 서버 통제 Refresh

**담당** 곽동욱 · `c9c622b`, `e4999c9`, `5965185` · [auth.md](auth.md#토큰)

- **배경**: 모바일 웹 중심 서비스. 요청마다 세션 저장소를 조회하지 않으면서도 로그아웃·탈퇴·비밀번호 재설정 때 **서버가 토큰을 통제**할 수 있어야 했습니다.
- **결정**
  - Access: 서명 검증만으로 인증하는 JWT(HS256, 1시간), 서버에 저장하지 않음.
  - Refresh: 7일, Redis `REFTOKEN:{userId}`에 **사용자당 1개** 저장. 재발급 때 저장된 값과 대조.
  - 로그아웃·탈퇴 시 access를 `BLACKLIST:{token}`에 **남은 만료 시간만큼만**(TTL = 잔여 수명) 등록.
  - 토큰은 응답 바디와 `HttpOnly; Secure; SameSite=None` 쿠키로 함께 내려주고, 요청에서는 **`Authorization` 헤더를 우선** 읽고 쿠키로 폴백.
- **근거**
  - 서명 검증만으로 인증하므로 요청마다 DB·세션 조회가 없습니다 `[분석]`.
  - Refresh만 서버가 쥐어, 재로그인·비밀번호 재설정 시 값을 덮어쓰거나 지우는 것만으로 다른 기기의 갱신 권한을 끊습니다 `[기록: TokenService 주석]`.
  - 블랙리스트를 잔여 수명으로 제한하면 만료된 토큰은 자동으로 사라져 Redis 크기가 "로그아웃된 유효 토큰 수"로 묶입니다 `[분석]`.
  - 헤더 우선은 일부 모바일 브라우저가 크로스도메인 `SameSite=None` 쿠키를 저장하지 않는 문제에서 비롯됐습니다 `[기록: AuthController 주석]` ([사례](troubleshooting.md#2-1-모바일에서-로그아웃회원탈퇴가-항상-실패)).
- **트레이드오프**
  - 인증 요청마다 블랙리스트 확인을 위한 Redis 조회가 1회 들어가 **완전한 stateless는 아닙니다**(필터 첫 단계).
  - Refresh가 사용자당 1개라 **다중 기기 동시 로그인이 불가**합니다. 나중 로그인이 이전 기기의 refresh를 무효화합니다.
  - 재발급 때 refresh를 교체(rotation)하지 않으므로 탈취되면 만료(7일)까지 유효합니다. rotation + 재사용 탐지가 다음 단계입니다.
  - 헤더 방식은 프론트가 토큰을 JS에서 보관하게 되어 HttpOnly 쿠키의 XSS 방어를 일부 포기합니다. 입력 차단과 쿠키 폴백으로 보완합니다.

## 2. 소셜 로그인 계정 정책 — 자동 연동하지 않는다

**담당** 곽동욱(카카오) · 김대현(구글) · `ee7dc3d`, `c655e9f`, `1f73c38` · [auth.md](auth.md#소셜-로그인-카카오--구글)

- **배경**: 일반 가입(이메일·비밀번호)과 카카오·구글 로그인이 공존합니다. 같은 이메일로 둘이 만났을 때 어떻게 할지 정해야 했습니다.
- **결정**
  - provider의 access token은 사용자 정보 조회에만 쓰고 **저장하지 않음**. 저장하는 것은 `provider`, `providerId`(provider 고유번호), 이메일, 이름뿐.
  - 재로그인 식별은 `(provider, providerId)` 유니크 키.
  - 이미 사용 중인 이메일이면 **자동 연동하지 않고 `409 EMAIL_CONFLICTED`**. 이메일을 받지 못하면 거부.
  - 소셜 계정은 비밀번호가 없으므로 재설정을 **API 진입 단계에서** 차단([사례](troubleshooting.md#2-5-소셜-로그인-계정의-비밀번호-재설정--정책은-마지막이-아니라-맨-앞에서-강제한다)).
- **근거**
  - "이메일이 같다고 같은 사람이라고 가정하는 대신 기존 방법으로 로그인하도록 유도" `[기록: AuthService 주석]`.
  - 이메일 소유 검증 수준이 provider마다 다르므로 이메일 일치만으로 계정을 합치면 계정 탈취 경로가 될 수 있습니다 `[분석]`.
  - provider 토큰이 DB에 없으므로 DB가 유출되어도 provider 계정에 접근할 자격 증명이 없습니다 `[분석]`.
- **트레이드오프**: 같은 이메일로 일반·소셜을 병행할 수 없습니다. 명시적 연동 흐름(로그인한 상태에서 provider 연결)과 카카오 연결 끊기 콜백은 아직 없습니다.

## 3. 참가자는 "모임별 신원"이다

**담당** 김대현 · `0ef9e88`, `3f1960d` · [domain-model.md](domain-model.md#참가자는-모임마다-새로-생기는-행이다)

- **배경**: 같은 사람이 여러 모임에 참여하고, 모임마다 프로필(학번·MBTI 등)이 다를 수 있으며, 관리자가 **계정 없는 오프라인 참가자**를 대신 등록해야 했습니다.
- **결정**: `Participant`를 사용자와 그룹의 연결 테이블이 아니라 **그 모임에서의 신원**으로 모델링하고, `user_id`를 NULL 허용으로 둡니다. 프로필은 임베디드 값 타입(`ParticipantProfile`).
- **근거**
  - 조 편성·투표·MVP 기록이 모두 `participant`에 매달려, **계정 유무와 무관하게 같은 로직**이 동작합니다(대리 참가자의 투표만 관리자가 대신) `[분석]`.
  - (group, user) 유니크 제약을 걸어도 MySQL은 NULL끼리 중복으로 보지 않아 대리 참가자를 여러 명 둘 수 있습니다 `[기록: Participant 주석]`.
- **트레이드오프**: 사용자 단위 통계(MVP 누적 등)는 집계 쿼리가 필요합니다. 대리 참가자는 본인이 수정할 수 없어 잘못 입력하면 삭제 후 재추가해야 합니다.

## 4. MVP 누적 횟수 — 카운터 대신 파생 집계

**담당** 곽동욱 · `0a27148`, `594d041`, `b5a6b79` · [vote.md](vote.md#mvp-누적-횟수)

- **배경**: 프로필·마이페이지에 "계정 누적 MVP 횟수"를 보여줘야 했습니다.
- **결정**: `User`에 카운터를 두지 않고 `participant.is_mvp`(그 모임에서 당선 여부)를 투표 마감 시점에 **한 번** 기록한 뒤, 누적은 `COUNT`로 구합니다(`countByUserAndIsMvpTrue`). 결과 조회와 확정이 **같은 메서드(`findMvpWinners`)** 를 쓰도록 추출했습니다.
- **근거**
  - "증가 로직을 빼먹었을 때 실제 데이터와 어긋나지 않도록" `[기록: Participant 주석]`. 원본 데이터에서 항상 파생되므로 불일치가 구조적으로 불가능합니다.
  - 결과 화면과 확정 기록이 같은 계산을 공유해 서로 다른 당선자가 나올 수 없습니다 `[분석]`.
  - 마감 호출(`finishVote`)이 투표를 끝내는 유일한 경로라 **정확히 한 번** 확정됩니다 `[기록: VoteService 주석]`.
- **트레이드오프**: 조회마다 COUNT 쿼리가 나갑니다(`user_id` FK 인덱스 범위 내). 규모가 커지면 `(user_id, is_mvp)` 복합 인덱스나 캐시를 검토합니다. 대리 참가자는 계정이 없어 항상 0입니다.

## 5. 조 편성 — NP-hard를 근사로 푼다

**담당** 김대현 · `513d2f2`, `f53c12d` · [assignment.md](assignment.md#알고리즘)

- **배경**: 성별·MBTI·학년·신입·직급 중 켜진 조건에 대해 같은 부류가 한 조에 몰리지 않게 나누면서, 조 인원은 고르게 하고, 고정 인원도 지켜야 합니다. 일반적으로 최적해를 구하기 어려운(NP-hard) 조합 문제입니다.
- **결정**: 참가자를 무작위 순서로 꺼내 **벌점이 가장 낮은 조에 배치하는 그리디**를 **20번 반복**하고, 그중 최선을 고릅니다. 비교 기준은 ① 조 간 인원 차이, ② 전체 벌점 순입니다.
- **복잡도**: 한 번의 그리디는 O(n²·c)(n 참가자, c 켜진 조건 수)입니다 `[분석]`. 참가자가 백 명 안쪽이라 20번을 돌려도 비용은 무시할 수 있습니다 `[기록: TeamAssigner 주석]`.
- **설계 포인트**
  - 계산만 담당하는 **순수 클래스**(저장·검증 없음)로 분리해 스프링 없이 단위 테스트합니다(`TeamAssignerTest`).
  - 경고 생성기(`AssignmentSummarizer`)를 분리해 "조건을 못 지킨 것"과 "구성상 애초에 지킬 수 없는 것"을 구분합니다. 관리자는 이 경고로 **재편성할지 그대로 확정할지** 판단합니다.
- **트레이드오프**: 최적을 보장하지 않고 셔플 때문에 결과가 비결정적입니다 → 확정 전에는 몇 번이든 재실행할 수 있게 UX로 풀었습니다. ILP·CP-SAT 같은 솔버는 최적을 보장하지만 외부 의존과 운영 부담이 커서 이 규모에서는 과투자로 판단됩니다 `[분석]`.
- **동시성**: 같은 그룹의 실행·확정은 그룹 행 비관적 락으로 직렬화합니다([사례](troubleshooting.md#3-1-동시-조-편성-요청-레이스--그룹-행-비관적-락)).

## 6. 상태 머신 · 멱등 전이 · 커밋 후 푸시

**담당** 김대현(상태 머신·SSE·멱등 전이 `b5838b4`) · 곽동욱(SSE 운영 이슈 대응) · [group-lifecycle.md](group-lifecycle.md)

- **배경**: 그룹은 8단계를 순서대로 진행하고, 관리자 화면에서 버튼이 중복 클릭·재시도되며, 참가자 화면은 상태 변화를 실시간으로 따라가야 합니다.
- **결정**
  - 상태 판정(`canAssign`, `isVoteFinished`, `canFinish` 등)을 **enum 메서드로 캡슐화**하고 `switch`에 `default`를 두지 않았습니다.
  - 전이 API는 이미 목표 상태면 **오류 없이 성공으로 조기 반환**(멱등).
  - 상태가 바뀌면 이벤트를 발행하고 `@TransactionalEventListener(AFTER_COMMIT)`에서 SSE로 전송합니다. 연결 직후 **현재 상태를 한 번** 보냅니다.
- **근거**
  - `default` 없는 switch 식은 상태를 추가하면 **컴파일러가 모든 판정 지점의 누락을 잡아 줍니다**.
  - 멱등이라 네트워크 재시도·더블클릭이 안전하고, 재시도가 예외로 돌아오지 않습니다.
  - 커밋 이후에 푸시하므로 **롤백된 변경이 참가자에게 전달되지 않습니다**. 연결 직후 현재 상태 전송으로 재연결 사이에 놓친 변경을 복구합니다 `[기록: GroupStatusNotifier 주석]`.
  - 알림이 서버 → 클라이언트 단방향이라 WebSocket보다 단순한 SSE로 충분하고, HTTP 인프라(Caddy 프록시·기존 인증)를 그대로 씁니다. 폴링보다 지연과 트래픽이 적습니다 `[분석]`.
- **트레이드오프**: 구독자 레지스트리가 **인스턴스 메모리**에 있어 단일 인스턴스를 가정합니다. 앱을 다중화하려면 Redis Pub/Sub 등으로 이벤트를 전파해야 합니다. 장기 연결의 자원 문제는 [사례 1](troubleshooting.md#1-1-장기-연결이-db-커넥션-풀을-고갈시킨-문제--osiv-원인-규명)에서 다뤘습니다.

## 7. 탈퇴는 소프트 삭제다

**담당** 곽동욱 · `b3c519d` · [auth.md](auth.md#회원-탈퇴)

- **결정**: `deleted_at`을 기록하고 이메일을 `withdrawn:{userId}:{원래 이메일}`로 바꿉니다. 로그인·JWT 인증은 모두 거부하며, 로컬 계정은 비밀번호로, 소셜 계정은 이미 통과한 JWT 인증으로 본인 확인합니다.
- **근거**: 이메일에 unique 제약이 있어 원래 값을 두면 재가입이 막히므로 값을 바꿔 반납하면서 행 자체의 유니크는 유지합니다 `[기록: User 주석]`. 조 편성·투표 이력이 깨지지 않습니다 `[분석]`.
- **트레이드오프**: 개인정보가 DB에 남습니다. 보관 기간 이후의 익명화·하드 삭제 배치는 아직 없어 [수동 삭제 절차](operations.md#회원-데이터-수동-삭제)로 대신합니다.

## 8. 에러 계약 — `code`로 분기한다

**담당** 김대현(공통 400 포맷 `27cceff`) · 곽동욱(인증 실패 사유 `7c63f3c`)

- **결정**: 모든 에러를 `{ code, message }`(입력 오류는 `errors` 맵 추가)로 통일하고, `ErrorCode` enum의 **상수 이름이 곧 응답 `code`** 입니다. 인증 실패도 사유별 코드로 수렴합니다.
- **근거**: 메시지는 문구가 바뀔 수 있으므로 클라이언트가 안정적으로 분기할 수 있는 식별자가 필요합니다. 필터·진입점·전역 핸들러가 서로 다른 계층이어도 한 형식으로 응답하게 됩니다 `[분석]`.
- **트레이드오프**: 코드가 곧 API 계약이라 이름 변경이 하위 호환을 깹니다. 일부 코드(`INSUFFICIENT_PARTICIPANTS` 등)는 HTTP 매핑이 잠정값이라는 TODO가 남아 있습니다.

## 9. 인프라 — 단일 호스트 Compose, 최소 노출

**담당** 곽동욱(Docker·CI/CD `eea1d90`) · 김대현(Caddy `fa9e74f`) · [architecture.md](architecture.md)

- **결정**: EC2 한 대에 Docker Compose로 Caddy · 앱 · MySQL · Redis를 띄우고, GitHub Actions가 이미지를 빌드해 배포합니다. 외부에 열린 것은 **Caddy의 80/443뿐**이고 앱(8080)·MySQL(3306)은 루프백에만 바인딩, Redis는 포트를 공개하지 않습니다. DB는 SSH 터널로만 접근합니다.
- **근거** `[기록: README]`: Nginx보다 설정이 적고 Let's Encrypt 인증서를 자동 발급·갱신하는 Caddy 선택, 로컬/운영 Compose 분리로 "내 컴퓨터에서는 되는데" 제거, 수동 배포 실수(옛 이미지 재기동·설정 누락) 제거.
- **트레이드오프**: 단일 장애점, 앱·DB 자원 경쟁, `latest` 태그만 사용해 롤백이 어렵고, CI에서 테스트를 건너뜁니다. 이는 의도적으로 단순하게 시작한 선택이며 개선 순서는 [한계와 개선 후보](architecture.md#현재-구조의-한계와-개선-후보)에 정리했습니다.
