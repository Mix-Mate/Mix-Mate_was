# 조 편성

> 설계 배경과 트레이드오프: [설계 결정 5 · 조 편성](design-decisions.md#5-조-편성--np-hard를-근사로-푼다) · 동시성 사례: [트러블슈팅 3-1](troubleshooting.md#3-1-동시-조-편성-요청-레이스--그룹-행-비관적-락)

참가자를 조건에 맞게 조로 나누는 기능입니다. 계산은 [TeamAssigner](../src/main/java/com/mixmate/domain/assignment/service/TeamAssigner.java), 경고 생성은 [AssignmentSummarizer](../src/main/java/com/mixmate/domain/assignment/service/AssignmentSummarizer.java), 저장·검증·동시성 제어는 [AssignmentService](../src/main/java/com/mixmate/domain/assignment/service/AssignmentService.java)가 맡습니다. 계산 클래스는 저장도 검증도 하지 않는 순수 로직이라 스프링 없이 단위 테스트할 수 있습니다.

## 흐름

| 단계 | API | 설명 |
| --- | --- | --- |
| 실행 | `POST /api/v1/groups/{groupId}/rounds/{round}/teams/generate` | 조 개수·조건·고정 인원을 받아 편성. 확정 전에는 몇 번이든 재실행 가능하며 매번 기존 결과를 덮어씀 |
| 확정 | `POST .../rounds/{round}/teams/confirm` | 라운드 시작(그룹 상태 전이). 되돌릴 수 없음 |
| 전체 조회 | `GET .../rounds/{round}/teams` | 확정된 뒤에만 조회 가능 |
| 내 조 조회 | `GET .../rounds/{round}/teams/my-team` | 내가 속한 조와 조원 |

`{round}`는 `FIRST_ROUND` 또는 `SECOND_ROUND`입니다. 1차는 참가자 전원이, 2차는 **2차 참여를 선택한 인원만** 대상입니다. 2차에 불참한 참가자는 2차 조회가 막힙니다.

## 입력 검증

- 조 편성은 `BEFORE_FIRST_ROUND`(1차) / `BEFORE_SECOND_ROUND`(2차) 상태에서만 실행할 수 있습니다.
- 한 명뿐인 조는 조가 아니므로 **대상 인원 ≥ 조 개수 × 2**여야 합니다. 부족하면 `INSUFFICIENT_PARTICIPANTS`.
- 라운드당 편성은 하나(`group_assignment`는 (group, round) 유니크)라서, 재실행은 새로 만들지 않고 기존 편성을 갱신합니다. 기존 조원은 먼저 지우고 다시 넣습니다.

## 조건 (`AssignmentCondition`)

조건은 켜고 끌 수 있고, 켜진 조건이 "같은 부류끼리 한 조에 몰리지 않게" 하는 기준이 됩니다.

| 조건 | 부류 나누는 기준 |
| --- | --- |
| `GENDER_BALANCE` | 성별 (남/여) |
| `MBTI_BALANCE` | 외향형(E) / 내향형(I) |
| `GRADE_SPREAD` | 학년 |
| `NEWCOMER_SPREAD` | 신입 / 기존 참가자 |
| `POSITION_SPREAD` | 운영진 / 일반 참가자 |

조 인원은 조건과 무관하게 **항상 고르게** 나뉩니다(켜고 끄는 조건이 아님). 학과 분산 조건은 제거되었습니다.

## 알고리즘

완전한 최적해(NP-hard)가 아니라 **그리디 + 반복 선택**의 근사입니다.

1. 고정 인원을 지정한 조에 먼저 넣습니다.
2. 나머지 참가자를 무작위 순서로 한 명씩 꺼내, "이 조에 넣으면 얼마나 나빠지는가"를 **벌점**으로 재고 가장 낮은 조에 넣습니다. 벌점은 켜진 조건마다 *그 조에 이미 있는 같은 부류의 수*를 더한 값입니다. 벌점이 같으면 인원이 적은 조로 보냅니다.
3. 1~2를 **20번** 반복하고, 그중 가장 나은 결과 하나를 고릅니다. 기준은 ① 조 간 인원 차이가 작을수록, ② 같다면 전체 벌점이 낮을수록입니다.

- 한 번의 그리디는 참가자를 꺼내는 순서에 좌우되어 운이 나쁘면 나쁜 편성이 나오기 때문에 여러 번 돌립니다. 참가자가 백 명 안쪽이라 20번을 돌려도 비용은 무시할 수 있습니다.
- 참가자 순서와 조 순회 순서를 섞기 때문에 **같은 입력이라도 실행할 때마다 결과가 달라집니다.** 마음에 안 들면 재실행하면 됩니다.
- 벌점을 센 값의 타입이 조건마다 다릅니다(전공은 `String`, MBTI 키는 `Boolean`). `==`로 비교하면 조용히 틀리므로 `Objects.equals`를 씁니다.

## 편성 경고

실행 응답에는 `warnings`(문자열 목록)가 함께 내려가고, 관리자가 **재편성할지 그대로 확정할지** 판단하는 근거가 됩니다. 경고가 없으면 빈 목록입니다. 두 종류가 같은 목록에 담깁니다.

1. **조건을 못 지킨 경우**: 값마다 조별 인원을 세어 가장 많은 조와 가장 적은 조의 차이가 **2 이상**이면 "○○ 균형/분산이 지켜지지 않았습니다." (인원이 조 개수로 나누어떨어지지 않으면 1명 차이는 피할 수 없어 허용)
2. **구성상 애초에 지킬 수 없는 경우**(성별·MBTI·신입·직급 조건): 한쪽 값만 있거나, 어떤 값의 전체 인원이 조 개수보다 적으면 "운영진 2명으로는 5개 조를 모두 채울 수 없습니다."처럼 알려 줍니다. 학년은 값이 많아 한 조에 특정 값이 없는 게 정상이라 이 검사에서 제외합니다.

## 동시성 제어

두 관리자 창에서 동시에 편성을 실행하면 서로의 조원을 지우고 넣다가 유니크 제약에 걸립니다. 확정 도중에 편성이 실행되면 이미 확정된 라운드의 편성이 바뀌는 문제도 있습니다. 그래서 **실행과 확정은 같은 그룹 행에 비관적 쓰기 락**(`findWithLockByGroupId`, `PESSIMISTIC_WRITE`)을 걸고 시작해 그룹 단위로 직렬화합니다.

락은 그룹을 읽기 **전에** 잡아야 합니다. 그룹을 먼저 읽어 두면 잠근 뒤에도 하이버네이트가 그 상태를 갱신하지 않아 낡은 값을 보게 됩니다.

## 명단이 바뀌면 편성은 초기화된다

참가자를 추가·삭제하면 이미 실행해 둔 조 편성은 함께 초기화됩니다. 명단이 달라진 편성은 틀린 결과이기 때문이며, 관리자가 다시 편성해야 합니다(`AssignmentResetter`).
